# Business rules matrix

| Business rule | Intended meaning | Where it lives today | Enforced by | Can be bypassed? | Risk if bypassed | Notes |
| --- | --- | --- | --- | --- | --- | --- |
| Only authorized Circle Up staff should use the Eventbrite facade | Prevent arbitrary use of the internal API | `eventbrite_api` middleware | App-layer bearer token in FastAPI | Yes, if token leaks; no API Gateway authorizer | Medium | Good enough for low volume, but boundary is inside Lambda |
| Event deletion should not be the first step once registrations exist | Avoid erasing live attendee context before cancellation/refund workflow | Streamlit delete UI | UI logic only | Yes, direct call to `DELETE /events/{id}?confirm=true` | High | Most critical business-rule gap |
| Venue deletion is not supported through the system | Prevent unsupported destructive action against Eventbrite | `eventbrite_api` | Hardcoded 501 response | No | Low | Clear and explicit |
| Event creation is only valid if event, ticket, questions and structured content all succeed | Avoid partial Eventbrite drafts presented as valid Circle Up events | `EventInstantiationManager` and basic create flow | Best-effort rollback in API | Partially; cleanup itself is best-effort | Medium | Transaction is logical, not atomic |
| Published events should include personalized minor authorization links | Ensure event listing points to the correct legal form and event context | `publish_event_instantiation` | API post-publish rewrite | Yes, if event is published outside this API | Medium | Important hidden coupling between publishing and legal flow |
| Only Eventbrite order webhook payloads with supported order URLs should materialize order snapshots | Avoid storing malformed or unrelated webhook traffic | `eventbrite_order_webhook` | `api_url` presence + host/path check | Yes, because handler trusts request source and only checks payload shape | High | Input origin not strongly validated |
| Only minors age 14 to 17 should enter the authorization workflow | Limit legal workflow to the intended attendee range | `eventbrite_order_webhook` | String match against attendee answer | Yes, if Eventbrite answer text changes or payload differs | Medium | Fragile because it depends on exact answer text |
| One minor attendee should correspond to one validation job | Avoid duplicated reminder/authorization flows for the same attendee and event | `minor_authorization_validator` | Job PK/SK dedupe | Mostly no once queued | Low | Nice idempotency point |
| A YouForm submission may reconcile a minor job only if it came from the configured authorized-minor form | Prevent unrelated forms from marking jobs as authorized | `youform_webhook` and validator | Exact configured `form_id` match | Hard to bypass through normal path; possible if webhook ingress is spoofed | High | Good local rule, weak external trust boundary |
| Minor authorization match must use email and event id together | Avoid matching the right email to the wrong event | `minor_authorization_validator` and `youform_webhook` | Query by email then filter by form id + event id | Partially, if event metadata is missing in the form | Medium | Better than email-only matching |
| Reminder emails should only go out while the order is active | Do not nag users after cancellation/refund | `minor_authorization_reminder` | Refreshed order status must equal `placed` | Low | Medium | Depends on webhook snapshot freshness |
| Reminder emails should stop after the event start time passes | Avoid stale operational outreach | `minor_authorization_reminder` | Event date/time + timezone gate | Partially, if datetime parsing fails | Medium | Parse failures degrade to “do not stop” |
| Unknown YouForm forms should not persist anything | Prevent random forms from contaminating storage | `youform_webhook` | Config-driven routing by `form_id` | Yes, spoofed internal-review pattern could still target background rows if ingress is spoofed | Medium | Routing is strict, ingress trust is not |
| Internal review submissions must attach to an existing background submission through a hidden partition key | Keep human review tied to the exact volunteer record | `youform_webhook` | Hidden `Partition key` parsing + exact form id | Partially, if a crafted valid partition key is posted | High | Business integrity depends on webhook trust |
| Volunteer proposal notifications should only go to approved admin addresses | Prevent leaking volunteer data to arbitrary recipients | `youform_webhook` | Hardcoded allowlist check over configured emails | Mostly no | Low | Nice explicit safeguard |
| Background-check review jobs should only be created from the configured compliance form | Prevent other forms from entering document review flow | `youform_webhook` and reviewer | Exact configured `form_id` gate | Possible through spoofed webhook + known form id | High | Again, local rule strong, ingress trust weaker |
| Only supported PDF documents should be reviewed | Keep reviewer focused on cedula and two certificate classes | `youform_webhook` and reviewer | Document-kind inference + allowlist | Yes, unsupported files are simply ignored | Low | Operationally safe but may hide missing docs |
| Cedula review must use the identity extraction path, not certificate OCR | Keep the higher-stakes ID logic on a specialized path | `background_check_reviewer` | Branch by `document_kind == cedula` | No in normal flow | Medium | Important business distinction |
| Final volunteer review status must aggregate across cedula and certificates | Prevent approval from a single isolated document | `background_check_reviewer` summary logic | Summary builder on review table | Partially, because missing docs produce `PENDING_DOCUMENTS` not `REJECTED` | Medium | Correctly modeled as aggregation |
| Ops should only receive one terminal notification per final background-check fingerprint | Avoid duplicate admin spam when nothing changed | `background_check_reviewer` | Fingerprint check before SES send | Mostly no | Low | Good idempotency pattern |
